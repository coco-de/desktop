ego lite 설치와 Claude Code·Codex·OpenCode 연동

이슈 #13 · feature/13-ego-lite-browser → main

무엇을 바꿨나

macOS 세팅 스크립트가 에이전트용 브라우저 ego lite를 설치하고, 팀이 쓰는 에이전트 3종(Claude Code·Codex·OpenCode)이 ego-browser로 쓸 수 있게 하는 절차(첫 실행·스킬 위치·권한 모드)를 스크립트·문서·실행 명령에 반영했습니다.

왜 이 방식인가

  1. cask가 없어 공식 dmg를 직접 받습니다. brew search --casks에서 ego lite를 찾을 수 없었고, 벤더 문서는 dmg 직접 설치(또는 에이전트가 설치 스크립트를 실행)를 안내합니다. 벤더 설치 스크립트는 격리 속성을 무조건 지우지만 이 스크립트는 지우지 않습니다. curl로 받은 파일에는 처음부터 격리 표시가 없고, 설치본에서 0건임을 확인했습니다.
  2. 체크섬이 없어 세 가지로 확인합니다. Apple 공증(spctl --assess), 서명이 깨지지 않았는지, 서명한 팀이 Citro Labs(Team ID JGQLC6YQYJ)인지를 codesign --verify --deep -R=<요구사항>으로 함께 봅니다. 처음에는 codesign -dv 출력에서 Team ID를 찾는 방식이었는데, 독립 리뷰에서 식별자에 TeamIdentifier=… 줄을 심은 가짜 앱이 통과한다는 지적이 나왔고 직접 재현했습니다. 요구사항 검사로 바꾼 뒤에는 진짜 앱은 통과하고 잘못된 팀·가짜는 막힙니다. --strict는 dmg 볼륨의 Finder 속성 때문에 정상 파일도 실패시켜 쓰지 않았습니다.
  3. 주소는 토큰 없는 egolite.dmg입니다. 공식 README의 egolite-<토큰>.dmg는 같은 파일(동일 ETag·크기)을 가리키는 별칭인데, 앱 번들 안의 벤더 설치 스크립트가 이 토큰을 마케팅 추적 코드(refcode)로 읽어 앱에 기록합니다. 그대로 쓰면 우리 설치가 그 캠페인으로 집계되고 코드가 바뀌면 다운로드가 끊깁니다.
  4. 에이전트 스킬은 앱이 설치하게 둡니다. 첫 실행(온보딩)이 ego-browser 명령과 Claude Code ~/.claude/skills, Codex·OpenCode ~/.agents/skills의 스킬을 설치합니다(벤더 가이드). 벤더의 npx skills add는 GitHub 저장소에서 스킬을 받는 방식이라 앱에 든 스킬과 버전이 어긋날 수 있고(가정), 어차피 명령은 앱 첫 실행이 만들어 미리 받을 이점이 없다고 판단했습니다. 대신 상태를 검증 줄과 안내로 보여 줍니다.
  5. 권한 모드는 에이전트별로 다르게 다룹니다. Claude Code는 팀 .zshrc의 claude()가 이미 --dangerously-skip-permissions로 실행하므로 추가가 없습니다. Codex·OpenCode는 계획 승인에서 "전용 실행 명령만 추가"를 선택해, 권한·샌드박스를 끄는 모드를 ego lite 작업 때만 쓰도록 codex-ego·opencode-ego를 만들었고 평소 codex·opencode 동작은 바꾸지 않았습니다. opencode-ego는 --auto를 인자 뒤에 붙입니다(서브커맨드 앞의 --auto는 프로젝트 경로로 읽힙니다).
  6. 중단돼도 부분 설치가 남지 않게 했습니다. 설치 폴더 안에 임시 이름으로 복사한 뒤 같은 폴더에서 이름만 바꿉니다(이름 바꾸기는 한 번에 끝남). 옮기기 직전에 설치 여부를 다시 확인해 내려받는 사이 설치된 앱 안으로 중첩되는 일을 막고, 임시 폴더는 rm -rf 대신 rmdir로 지워 마운트가 남아도 읽기 전용 볼륨 안을 건드리지 않습니다. EXIT 트랩 안에서는 set -e가 다시 적용되므로 hdiutil detach 실패에 || true를 붙였습니다(없으면 마운트 전에 끝나는 실패에서 정리가 끊겨 받다 만 dmg가 남았습니다).

여기부터 리뷰하세요

  1. install_ego_lite(macos/mac-setup.sh 781~838행): 실패 경로마다 경고 후 exit 0인지, 서명 게이트(spctl + codesign --verify -R)가 복사보다 먼저인지, 설치 폴더 안 임시 복사 → 이름 바꾸기 순서와 트랩 정리.
  2. 회귀 테스트: codesign 스텁이 -dv 출력에 진짜 팀 줄을 섞어 두어 출력 문자열을 믿는 구현을 잡는지, hdiutil detach가 마운트 전에 실패하는 실제 동작을 흉내 내는지.
  3. 10단계 검증 줄(2494행 부근), 마지막 안내 10~12번(번호·하위 항목 순서), macos/.zshrc의 두 함수(262~263행).
  4. README 에이전트별 사용법 표가 벤더 가이드와 맞는지, windows·linux 사유 행.

로컬 검증

  • 실제 공식 dmg(arm64)로 설치 함수를 실행했습니다(설치 위치만 임시 폴더로 변경). 설치, 재실행 시 건너뜀, 임시 폴더 0개, 남은 마운트 0개. 설치본은 Gatekeeper 수락(공증)·Team ID 일치·격리 속성 0건이었습니다. Intel dmg도 번들 이름·서명자·공증이 같음을 확인했습니다(설치는 하지 않음).
  • 서명 게이트: 진짜 앱 통과, 잘못된 팀 차단, 식별자 스푸핑 앱은 옛 방식이 통과시키고 새 방식이 차단함을 같은 환경에서 비교했습니다.
  • 다른 디스크(스파스 이미지)에 설치하며 복사 도중 SIGTERM·SIGKILL을 보냈을 때 최종 경로 ego lite.app에 부분 설치가 남지 않았고(SIGTERM은 임시 폴더까지 정리, SIGKILL은 숨김 임시 폴더만 남음), 재실행하면 정상 설치됐습니다. 내려받는 사이 다른 곳에서 앱이 설치되는 경쟁 상황도 재현해 남의 앱이 그대로 유지됨(중첩 없음)을 확인했습니다.
  • 합성 dmg로 실제 hdiutil·ditto 경로의 시나리오(정상, 공증 실패, 서명자 불일치, 스푸핑, 앱 없는 dmg, 깨진 dmg, 다운로드 실패, 경쟁 설치)를 실행했고, 실패 시나리오는 모두 경고 후 스크립트가 계속 진행되고 정리됐습니다.
  • Python 회귀 검사 24개 통과(기존 12 + 신규 12). 변이 검사 10종(정리 누락 · 옛 grep 서명 게이트 · 공증 제거 · Rosetta 판별 제거 · 멱등 검사 제거 · 이름 바꾸기 전 재확인 제거 · -readonly 제거 · curl -f 제거 · 안내 번호 중복 · 임시 복사본 정리 제거)를 각각 넣었을 때 모두 테스트가 실패했습니다.
  • macOS·Linux Bash 문법 검사, zsh -n, diff 공백 검사 통과. ShellCheck 경고 3건은 기본 브랜치에도 같은 코드에 있으며 새 경고는 0건입니다. codex-ego·opencode-ego는 가짜 실행 파일로 플래그와 인자 순서를 확인했습니다.
  • 코드 리뷰: /cc-quality:review --quick --gate-mode 9개 항목 판정(치명 0 · 확인 못 함 0). 별도 서브에이전트의 독립 리뷰는 10건을 보고했고(Major 2 · Minor 5 · Nit 3 + 한계 관찰), 직접 재현해 확인한 뒤 Major 2건을 포함해 대부분을 위 커밋으로 반영했습니다. 반영하지 않은 것은 아래 "범위 밖"에 이유와 함께 적었습니다.
  • 미검증: 실제 /Applications 설치와 ego lite 첫 실행(온보딩) 화면, 각 에이전트에서 스킬이 실제로 불러와지는지(권한 모드·터미널에서의 스킬 호출 방식), Gatekeeper가 꺼진 환경에서의 spctl 동작, Windows PowerShell 검사(로컬에 pwsh가 없고 이번 변경에 PowerShell 파일이 없어 CI가 실행).

실행 기록

계획 승인 후 구현부터 머지까지 진행하는 정책(원스톱)입니다. 이 저장소는 접근 가능한 ZenHub 워크스페이스에 연결돼 있지 않아 작업 기록은 GitHub 이슈·PR에 남기며, 보드 타입·포인트·파이프라인은 반영되지 않습니다(#9와 동일). 규모(단독 Feature·5 SP)와 요구사항 정리는 작업자가 직접 판단했고 별도 보조 판정·서브에이전트는 쓰지 않았습니다. 제품 화면 개발이 아니라 디자인 결정 기록은 없습니다. 독립 리뷰어는 머지 전에 결과를 받아 반영했습니다.

범위 밖

  • Windows·Linux 설치: 벤더 빌드가 아직 없어 미지원 사유만 README에 남겼습니다. 출시 시 반영은 #14로 추적합니다.
  • Chrome·Dia용 ZenHub 확장 자동 등록과 번역 언어 설정을 ego lite로 넓히는 일: 동작을 확인하지 못한 영역이라 제외했습니다.
  • codex·opencode 기본 실행의 권한 우회: 모든 사용에서 샌드박스가 꺼지는 팀 정책 변경이라 승인 없이 바꾸지 않았습니다.
  • ego lite 온보딩 화면 자동 조작과 에이전트 스킬 선설치: 앱이 직접 처리하는 단계입니다.
  • 알려진 한계(리뷰에서 확인, 이번에는 바꾸지 않음): 최신 macOS에서 hdiutil attach/detach가 deprecated로 표시됩니다(지금은 동작하고 벤더 설치 스크립트도 사용). 사라지면 경고 후 수동 설치 안내로 떨어집니다. hdiutil attach 중 Ctrl-C는 hdiutil이 정상 종료해 스크립트가 계속 진행됩니다.
  • 후속 확인 후보: 리뷰어가 앱 번들에서 ego lite 온보딩이 ~/.codex/rules/default.rules에 ego-browser 허용 규칙을 쓰는 것으로 보이는 문자열을 발견했습니다. 사실이면 Codex는 전체 샌드박스 해제(codex-ego) 없이도 될 수 있습니다. 실제 온보딩 후 확인이 필요해 이번에는 벤더 가이드대로 두었습니다.
